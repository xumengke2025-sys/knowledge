# 商业航天与卫星互联网｜标准、科研与证据框架 v0.6

这是一件给 FirmBuddy 行业专家长期装备的**判断框架**，不是企业静态数据库。企业当前专利、财务、年报和新闻应在运行时通过 MOSS/交易所等工具获取，再用本框架解释。

## 1. 标准与测试方法地图

### 基于低轨卫星互联网的航空监视技术要求（20264606-Z-469）
- 状态：制定中；主管/归口：全国宇航技术及其应用标准化技术委员会
- 专家用途：低轨卫星互联网承载航空监视、链路与系统要求
- 来源：https://std.samr.gov.cn/gb/search/gbDetailed?id=5A4E35E2306DA6D6E06397BE0A0A8154
- 使用纪律：标准状态、版本和实施日期必须以当前官方页面为准；标准计划不等于已实施标准。

## 3. 动态学术检索主题包

- `LEO satellite internet NTN handover routing`
- `inter satellite link optical communication LEO`
- `satellite phased array beam hopping gateway diversity`
- `regenerative payload software defined satellite`

建议每周按主题在 OpenAlex/Crossref/Semantic Scholar/arXiv/ChinaXiv/PubScholar 等渠道发现新成果。新论文先进入 Radar candidate；只有复核方法、对象、测试条件和边界后，才升级为稳定机制知识。

## 4. 企业运行时核查问题

- 公司技术属于卫星平台、载荷、终端、网络还是发射
- 是否有在轨验证而非仅地面样机
- 吞吐/时延/EIRP/G/T是否说明链路预算条件
- 星间链路是否有捕获跟踪与在轨链路证据
- 火箭是否有复飞而非仅回收
- 订单是否明确对应商业航天而非军工/北斗共用业务

## 5. 证据升级协议

### Radar → 稳定行业知识
- 必须落到技术树节点；必须说明研究对象、实验/仿真条件、基线、指标与边界。
- 单篇论文、单个预印本或媒体报道只能形成候选信号。
- 能改变原有路线判断时，应明确“改变了哪条机制/benchmark，以及什么条件下成立”。

### 企业自述 → 已确认企业事实
- 先锁定法律主体；优先法定披露、交易所、标准化测试或可核查官方材料。
- 企业论文作者单位、科研合作、集团研究院成果不能自动归因给上市主体。
- 阶段词必须保持原义：研发、样机、送样、验证、中试、小批、批量、规模化不可互换。

### 专利 → 技术证据
- 申请人/子公司归一、专利族、法律状态、摘要/权利要求与技术节点映射缺一不可。
- 专利件数不能直接用于技术实力排名。

## 6. 快速企业结论模板

1. 技术位置：落到哪些 taxonomy 节点；哪些只是相邻能力。
2. 技术路线：公司采用什么路线，机制上的优点/约束是什么。
3. Benchmark：披露参数是否具备可比测试条件；不能比较时明确原因。
4. 产业化阶段：逐产品/路线判断，不给公司一个笼统量产标签。
5. 专利结构：按技术簇、代表专利、家族/法律状态缺口描述。
6. 财务交叉验证：研发、存货、在建工程、现金流只能验证产业化承载，不能证明技术先进。
7. 最近变化：近12个月政策、标准、论文、产品、验证与交付变化。
8. 强项/未知：只写有证据的强项；至少列一个会改变结论的证据缺口。

## 7. 禁止推断

- 不把论文结果直接赋给企业。
- 不把标准起草单位身份等同于产品满足该标准。
- 不把项目/中试/认证申请写成量产。
- 不把媒体转载数量当成多源证据。
- 不输出投资评级、商机触发或成交概率。
